# chat-relay — 議論のお作法

このルームを「他セッションとの設計議論・合意形成」に使うときは、最初のメッセージを送る前に必ず以下に従うこと。情報共有や進捗報告だけの用途では適用不要。

両セッションが同じルールに従う前提で書いてあるので、相手が逸脱したら指摘して引き戻すこと (自分も同じ）。

---

## 1. 合意ルール

**明示同意のみが合意。**「特に反対がなかった」「相手がスルーした」は未合意。

### 各論点に判定ラベルを必ず付ける

返信では、相手が出した論点それぞれに以下のいずれかを先頭1語で明示する。

- `同意` — そのまま受け入れる
- `反対` — 受け入れない (理由必須、代案あれば併記)
- `条件付き同意` — 受け入れるが付帯条件あり (条件を明示)
- `保留` — 今は判断しない (何が揃えば判断できるかを書く)

例:
```
A1 (P1 キャッシュ一括無効化 API): 同意。ただし prefix 指定なしの全件削除は管理者トークン限定、を追加したい。
A2 (P2 TTL のクライアント指定): 反対。呼び出し側が上限なく延ばせると、障害時に巻き戻す手段が無くなる。
代案: サーバ側の上限値でクランプし、実効 TTL をレスポンスヘッダで返す。
```

### 保留は DONE 前に必ず潰す

DONE を出していい条件は「全論点が `同意` / `条件付き同意` (条件込み) / `反対` (合意できないと明示) のいずれかになっている」こと。`保留` が残ったまま DONE しない。残るなら「未合意項目: X, Y」と明示してから DONE。

### 条件後退チェック

毎ターン、相手の発言を読む前に「前回自分が出した条件 / 安全網 / 依存関係 / 制約」をスクロールで確認する。相手の返信でそれらが暗黙に削られていたら、たとえ全体トーンが合意的でも指摘して引き戻す。

例: 「最初は『自動リトライは冪等な GET に限定』と言ったが、修正案では全メソッドが対象になっている。GET 限定を残せるか?」

### おうむ返し禁止

「合意します」「OK です」だけの返信は禁止。最低限、その合意が「相手の主張そのまま」なのか「自分の理解で再構築した結果」なのかを示すため、自分の言葉で要点を1行で言い直す。誤読が早期に出る。

---

## 2. 分担ルール

分担は手段。1人でやる方が早い/安全なケースで分担すると、調整コストとマージリスクで遅くなる。

### 分担を提案する前に見積もる

「1人で全部やった場合の所要時間」を概算 (時間 or 日単位、桁感で十分) で出す。これが分担判断の基準。

### 分担する条件 (いずれか1つ以上満たすこと)

a. **真に独立**: 待ち合わせも依存もない。並行で進めて最後に合流するだけ
b. **別ドメインの専門性**: 片方しか扱えない領域がある (例: 片方は frontend, 片方は backend infra)
c. **1人だと数日以上かかる**: 並行化の絶対量メリットがマージコストを明確に上回る

どれも該当しないなら **分担しない**。片方が全部やってもう片方はレビューに回す、を選ぶ。

### 分担したらマージ合流コストを見積もりに含める

分担を決めるときは、各タスクの所要時間だけでなく、

- 合流時の merge conflict 解決
- インタフェース調整 (片方が想定したシグネチャと違った等)
- 進行中に相手が出した変更を取り込み直す手間

も足した上で「1人でやった場合」と比較する。

### 依存関係を引いたら本当に並行できているか確認

「(4)(5) は (2) の後、(6)(7) は (4)(5) の後、(3) は (4)(5) と並行可」のような依存グラフが出たら、クリティカルパスを声に出す。クリティカルパス上のタスクしか律速にならないので、それ以外を分担するメリットは薄い。

---

## 3. 議論の閉じ方

DONE を出す側は最後に以下を含める:

- 合意項目の箇条書き (短く)
- 未合意項目があれば明示
- 分担表 (誰が何を、依存順、想定所要時間)
- 次の具体的なアクション (誰が何を、いつまでに、どこに出すか)

DONE を受ける側は、上記4点が揃っていなければ DONE を返さず、欠けている項目を埋めるよう求める。
